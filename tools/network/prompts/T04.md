# TASK T04 — durable event log, scheduler, outbox, reconciliation, pause

Deliverable: `src/rarepipe/stages/network/eventlog.py`, `network/scheduler.py`, `network/outbox.py`.
Tests: `tests/test_network_t04.py`. Acceptance: A12, A13, A14, A30. Depends on T02's model.

Build the durable substrate the rest of the workflow runs on. Follow the storage idiom already proven
in `src/rarepipe/stages/prospective/store.py`: exclusive-create for immutable records, atomic replace
for pointers, a fallback when the filesystem has no hard links (the case drive is exFAT/NTFS), and an
append-only audit log that records ids, kinds and reasons but never payload contents.

**Event log**: append-only, each event carrying id, timestamp (UTC), previous state, new state, the
reason, and the actor. Events are immutable. Provide replay of a task's history.

**Scheduler**: durable timers in UTC, with local-time display left to the view layer. Every waiting
task has an owner AND a next trigger, or an explicit `UNSCHEDULED` state with a visible reason —
model this so a waiting task with neither is impossible to construct. Respect configured recipient
quiet hours. No polling loop that re-fires merely to look busy: a follow-up must have a bounded
count and a reason.

**Outbox**: idempotency keys, at-most-once dispatch attempts, and reconciliation. If a provider
accepts a send but the client times out, the state becomes `DELIVERY_UNKNOWN` and MUST be reconciled
before any retry — a retry from `DELIVERY_UNKNOWN` without reconciliation must be refused by the code,
not by convention. Do not claim exactly-once delivery.

Implement the state machine: DRAFT → READY → DISPATCHING → SENT → WAITING → RECEIVED → ASSESSED →
CLOSED, with alternates AUTHORIZATION_REQUIRED, CONTACT_UNVERIFIED, DELIVERY_UNKNOWN, PAUSED,
DECLINED, EXPIRED, FAILED. Every transition records an event and a reason. A delivery receipt is NOT
a response: make that structurally clear.

Cadence and spend limits have NO permissive defaults. Unset limits leave live dispatch blocked while
still allowing preparation. Pause and cancel must preserve recorded history and produce a permitted
handoff.

Your tests must assert:
- A12: a waiting task cannot exist without an owner and next trigger unless explicitly unscheduled
  with a reason.
- A13: duplicate sends deduplicate by idempotency key; a `DELIVERY_UNKNOWN` send refuses a retry
  until reconciled.
- A14: unset cadence/spend limits block dispatch; preparation still works.
- A30: pause and cancel keep the full event history and yield a handoff.
- A delivery receipt does not advance a task to RECEIVED.

Do not implement authorization policy, message composition or transport; T05 owns those.
